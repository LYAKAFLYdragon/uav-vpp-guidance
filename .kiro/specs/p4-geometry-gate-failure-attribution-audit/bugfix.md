# Bugfix Requirements Document

## Introduction

The authorized run `GEO-20260713-R1` (geometry pretrain only, 200,000 steps per skill) completed with the verdict `all_skills_ready_for_combat_finetune = false` and the hard constraint `do_not_start_combat_finetune`. All four skills (`pursuit_conversion`, `lead_intercept`, `defensive_extension`, `reentry_recovery`) pass profile coverage and safety; all four fail phase coverage; three (`defensive_extension`, `lead_intercept`, `pursuit_conversion`) additionally fail intent progress, while `reentry_recovery` passes intent progress but remains blocked by phase-coverage failure.

The bug being fixed is **not** the gate verdict itself — the gate correctly emitted a `false`/blocked result, and that result is legitimate negative evidence. The bug is a **defect in the failure-attribution and status-reporting process**: the current project state does not provide a traceable, per-skill × per-cell explanation of *why* the gate failed, does not distinguish "field absent (unverifiable)" from "field present with value 0", does not reconcile the declared cells against the cells actually emitted by the gate (verified reconciliation: 26 declared / 26 emitted / diff 0), does not record the strict provenance boundary that separates the currently available D: drive artifacts from the missing frozen run inputs, has no controlled label for a contract/provenance inconsistency, and the execution checklist (`reports/thesis_five_state_shared_intent_v1_execution_checklist_20260713_zh.md`) still represents P4 as `in progress` (`[>]`) rather than as a completed run yielding formal negative evidence. This produces an ambiguous, non-auditable state that blocks a correct next-step decision.

A second structural limitation must be stated up front: the coverage recording logic keys each step by the scenario's fixed `initial_class`, not by a per-step re-classified live posture. See `_record_episode_summary` at `src/uav_vpp_guidance/training/thesis_shared_skill_geometry.py:451` (which writes `state_phase_steps[f"{initial_state}:{metric['phase']}"]`) and its call sites at line 806 (training) and line 677 (dev30), both of which pass `scenario["metadata"]["initial_class"]`. Therefore this audit can only prove coverage of "initial posture label × phase" (**initial-class × phase**). It CANNOT prove whether the dynamic five-state posture actually occurred during `post_merge` / `re_entry`. This limitation must be carried explicitly through the matrix column semantics, the conclusions, and the confidence ratings.

The "fix" (`F'`) is to produce a correct, evidence-backed attribution audit and to update the checklist to its final P4 negative-evidence state. The fix explicitly does **not** attempt to make P4 pass, does not retrain, does not relax or modify the pre-registered gate, and does not modify any P4 outputs, checkpoints, model, reward, or the canonical two-skill paper mainline.

This is a strictly non-training, non-tuning attribution audit. Work must be performed on branch `research/thesis-five-state-shared-intent-v1` after syncing the remote; if unrelated local changes exist, a separate git worktree must be used rather than resetting or overwriting local state.

## Bug Analysis

### Current Behavior (Defect)

When a reviewer or downstream decision process inspects the state of `GEO-20260713-R1` to decide whether combat finetune is allowed, the current process behaves defectively:

1.1 WHEN a completed P4 gate result exists with per-skill failing fields (phase coverage for all four skills; intent progress for three skills) THEN the system provides no per-skill × per-cell attribution matrix explaining which specific initial-class × phase cells drove each failure and why.

1.2 WHEN a declared geometry-phase cell was emitted with value 0 (verified zero-step declared cells: `defensive_extension` disadvantage:post_merge, disadvantage:re_entry, neutral:post_merge, neutral:re_entry; `lead_intercept` advantage:post_merge, neutral:post_merge; `pursuit_conversion` advantage:post_merge, neutral:post_merge; `reentry_recovery` advantage:post_merge, advantage:re_entry, neutral:post_merge, neutral:re_entry) THEN the system does not trace each such present_value_0 cell back to a specific JSON/config/manifest/source field with evidence and counts. NOTE: on the currently available artifacts all declared cells are PRESENT (reconciliation is 26 declared / 26 emitted / diff 0), so the dominant case is `present_value_0`, not absent; any earlier framing of these cells as "missing"/"absent" is an unverified historical premise, not a fact about the P4 gate.

1.3 WHEN a cell's coverage is inspected THEN the current reasoning risks conflating two distinct situations: (a) the field EXISTS in `selected_gate.geometry_phase_coverage` with value 0 — which the gate legitimately emits for a declared cell that never appeared (`thesis_shared_skill_geometry.py:544` writes 0 via `combined["state_phase_steps"].get(..., 0)`); versus (b) the field does NOT exist at all in the emitted coverage map. The current process treats both as interchangeable and risks asserting a cell is "physically impossible" purely from its absence, rather than reporting (a) as a legitimate 0-step count under current gate semantics and (b) as unverifiable.

1.4 WHEN a failure occurs THEN the system does not distinguish `not_observed_cannot_assess` / `train_coverage_gap` (the skill was never given the chance to demonstrate the behavior) from `observed_behavior_failure` (the skill was observed and behaved incorrectly), and does not separate a train-vs-dev divergence (a declared cell with train steps > 0 but dev30 = 0, e.g. `lead_intercept` advantage:post_merge with train = 2920 and dev = 0) from a genuine train-coverage gap (train-absent/0 and dev = 0), leaving the attribution ambiguous.

1.5 WHEN the execution checklist is read THEN P4 is represented as `in progress` (`[>]`, single skill `pursuit_conversion` still training) rather than as a completed run in which all four skills reached 200k steps and produced formal negative evidence, misrepresenting the true project state.

1.6 WHEN the numeric evidence for the verdict is requested THEN there is no frozen record of the result JSON file SHA256, the list of JSON top-level fields, the run commit SHA, and each skill's gate fields and numeric values, so the evidence backing the verdict is not reproducibly traceable, and the frozen run provenance cannot be distinguished from the current working-tree source.

1.7 WHEN the attribution conclusion is consulted for a next-step decision THEN there is no single explicit, evidence-backed statement of whether combat finetune is allowed, leaving the `do_not_start_combat_finetune` decision without a documented rationale.

1.8 WHEN the declared cells are compared against the gate output THEN the current process performs no explicit reconciliation between declared cells and gate-emitted cells, and — worse — earlier attribution relied on a HISTORICAL PREMISE THAT IS NOT VERIFIED BY CURRENTLY AVAILABLE ARTIFACTS, namely that the declared count was 26 while only 22 cells were emitted, leaving 4 declared-but-not-emitted `crossing_entry`-related cells for `lead_intercept` and `reentry_recovery`. That 26/22/4 premise is empirically disproven against `src/p4_geometry_pretrain_gate.json`, the four `src/skills/<skill>/geometry_pretrain_summary.json`, and the registry: the verified reconciliation is 26 declared / 26 emitted / diff 0 / extra 0 for every skill (`pursuit_conversion` 6/6, `lead_intercept` 6/6, `defensive_extension` 6/6, `reentry_recovery` 8/8), and a 22-emitted output is structurally impossible because `evaluate_skill_gate` (`thesis_shared_skill_geometry.py:511-546`) emits the full Cartesian product of declared `geometry_states` × `phases`, filling absent combinations with 0. The genuine defect is therefore the absence of an explicit reconciliation record and per-cell attribution of the declared cells emitted with value 0, NOT any declared-vs-emitted difference.

1.9 WHEN the frozen provenance inputs (the run commit SHA, `training_plan.json`, and `resolved_geometry_config.json`) are missing and the unverifiable historical 26/22/4 premise cannot be checked against them THEN the existing five attribution labels cannot describe this situation, so a contract/provenance inconsistency risks being misclassified as skill capability failure or physical unreachability instead of being surfaced as a provenance/coverage-semantics issue. NOTE: on the currently available artifacts the declared-vs-emitted difference is 0, so a `contract_or_provenance_mismatch` on THIS artifact is triggered by the missing provenance inputs and the unverifiable historical premise, NOT by any declared-vs-emitted diff.

1.10 WHEN a matrix column labeled "state × phase" is interpreted THEN the current process implies the dynamic five-state posture was observed at each phase, even though the recording logic keys steps by the scenario's fixed `initial_class` (`thesis_shared_skill_geometry.py:451`, call sites at line 806 and line 677), so claims about dynamic posture in `post_merge` / `re_entry` are unsupported by the recorded data.

### Expected Behavior (Correct)

2.2 WHEN a declared geometry-phase cell was emitted with value 0 (`present_value_0`) THEN the system SHALL individually verify and attribute that cell (never copied blindly), linking every number back to a specific JSON/config/manifest/source field path with evidence and counts. The system SHALL base attribution on the verified reconciliation (26 declared / 26 emitted / diff 0) and SHALL NOT describe any declared cell as "missing"/"absent" on the currently available artifacts; the absent-vs-present-value-0 distinction remains valuable analytically, but the system SHALL report that on this artifact all declared cells are PRESENT, so the dominant case is `present_value_0`.

In neither case SHALL the system infer "physically impossible" from mere absence; a claim of structural non-observability SHALL require manifest initial geometry + phase rules, and even then SHALL honestly report the absence of raw per-step evidence.
